# V1.0 生产任务数据中心

## rw38.4 逐站预计工作量

预计流入由与开战共用的维修路线生成。数据中心按工序计次，模拟只在路线首站建立一个物理批次。BD 与 POL 流经 PI，贴膜完成后进入 VI。VI 合并显示 NDF 和维修后流入的合计，并列出两种来源。实际出货使用同一 VI 员工的有限工时，MNT 按 OC、LCM 分道。数据中心与复盘均将待检、待出货放在同一岗位行，结算仍保留真实出货量及原始 OUT 目标的考核。

黑胶＝四舍五入（本班 POL NG × 黑胶比例）。MNT 切割＝四舍五入（本班 POL NG × 切割比例），TV 没有切割岗位。比例可来自计划 `productionPlan.ratios[BU][DAY 或 NIGHT].blackRatio / cutRatio`（0～1），或来自数据中心「开战前确认」中显式录入的现场比例（0～100%），按日期、BU、班次保留在当前页面。显式确认优先。缺少比例显示「待确认路线」，0% 显示为 0。旧计划的型号布尔值与 `filmBlack` 不参与这两项估算。生产文件中的比例值仍待现场核对。

脱 POL 的预计工作量为一遍 POL 流入，总工作量说明另显示撕、贴的期初与预计处理次数合计。贴胶「预计新增工作量」显示新增 COF，「总工作量／说明」单独显示含祛除、BD 期初的总 COF。

表中 VI 是入站需求，实际 OUT 由班次模拟的检验结果和工时决定。白班物理预测投入为 TV 621 片、MNT 1744 片。完整浏览器用例同时检查夜班切换、COF 变化、未确认条件、重复导入和待检／待出货合并显示。

从游戏顶部打开「生产任务数据中心」，点击「导入今日生产任务」，选择 V3.8 提取器生成的合并 JSON。核对 TV、MNT 和两个班次的数据后，点击「确认导入」。再次导入会同时替换期初、目标和计划。目标随当前页面任务保存，刷新后需要重新导入。旧版单日报仍可导入，计划显示「未导入」。

V3.8 的根节点为 `date / rows / targetBaseline / source / productionPlan`。目标来自 `targetBaseline.rows[].target`，期初来自 `rows[].today`。计划的 `dayQty / nightQty` 和 `expectedDay / expectedNight` 分别对应白班和夜班。换班时使用同一份期初和目标快照。工序存在数值但无法映射时，预览列出原始名称和位置，失败会保留上一份任务。已导入的计划确认该站无需求时显示 0，缺失数据或比例分别显示「未导入」或「待确认路线」。

TV、MNT 先按尺寸归属，再对 MNT 的 NDF 按型号自动识别，优先级为 BAB 前缀、第 10 位、第 8 位。界面显示无法识别的型号和数量，并保留原任务直到来源可完整验证。其他需要 VI 的 MNT 预计产品进入 OC VI。计划使用各自班别的四类预测字段。FA、Disa 和未分区共享数据排除在维修任务外。共享黑胶分配为 TV 20%（四舍五入）、MNT 取余量，已分配的黑胶保持原值。

数据中心网页页头显示 `V1.0-rw38.4`，Windows 提取器保留 `rw38.3`。期初和目标分别按 Excel 指标单元格的 `mergeArea` 聚合。独立区域各自计数，同一区域冲突会列出两条 JSON 记录及其坐标。共享黑胶按区域识别后拆分。旧 V3.8 JSON 没有区域坐标时，仅在 `rw-win7-vbs` 来源包含本次确认的全部七组岗位及行号时应用该旧模板兼容规则。其他布局应从修订版 WIP 提取器重新导出。

### rw38.4 收尾回归

- 浏览器检查页头、标题和数据中心显示同一版本号。
- 本班输入百分比后，核对预计工作量与模拟批次；导入不同比例后，核对 TV／MNT、白夜班作用域和四舍五入。比例缺失保持待确认，明确的 0% 显示 0，非法比例触发回滚。
- 输入相反的旧 `polBlack`／`cut` 标记、`filmBlack:true` 及相反的 `PANELTYPE`／`OUTTYPE`，确认网页仍分别按数值比例及型号编码计算。引擎用例另验证显式贴膜黑胶标记不会增加黑胶工序。
- 白班分别校验新增 COF 和含期初总 COF，换班和参数变化后重新核对。二次导入更新期初、目标和计划，保持物理批次数守恒。

比例的自动化验收覆盖真实配置读取路径，使用脱敏数值。仍需核对现场使用的 TV／MNT 白夜班比例来源和值、原维修 SQL 规则和真实型号、Excel COM 及公司浏览器实机。本轮未在公司环境执行这些项目。

## rw38.3 对账记录

根因是旧提取器把合并区域左上角值带入每个物理行，而旧网页按物理行累加。型号路线依赖手选，且网页重新由计划量推算预测，容易在取整边界偏离导出值。本次使用指标区域身份去重，并保留导出的班次预测后再按既有最大余数法分配整数片数。

## Windows Excel COM 验收

1. 在装有 Excel 且允许 Windows Script Host 的公司电脑运行 `cscript.exe //nologo Read-RW-WIP.vbs --merge-self-test`。只建立一个内存中的合成工作簿，期初 12、目标 123 应各读取一次，黑胶拆为 11／44。
2. 双击同一目录的 `Read-RW-WIP.bat`，确认启动行显示 `rw38.3`。打开有权限的日报并保存到获准目录。核对 49–50 等对应区间的 `mergeArea` 及各指标记录数量。
3. 在同一目录执行 `.\Join-RW-Plan.ps1 -WipPath .\rw-wip.json -PlanPath .\rw-combined-old.json -OutputPath .\rw-combined-new.json`，把文件名改为同日实际文件名。导入新文件并对照上表及两个班次的预测。

开发环境未注册 Excel COM，Windows Script Host 返回访问拒绝。PowerShell 合并脚本通过语法检查，实际执行被本机脚本策略阻止。真实区域读取、合并工具运行和公司日报尚待现场验收。

贴胶工作量按祛除和 BD 的期初及预计新增之和乘以所选班次 COF/片。脱 POL 工作量按撕 POL 和贴 POL 的期初及预计新增求和。脱 POL 的展示期初含撕 POL 期初和本 BU 的原始脱 POL 期初，目标为 0。引擎只在原始工序建立物理批次。只有 POL 汇总数时，整批从撕 POL 进入，之后继续贴 POL，免去手动拆分。同份日报同时有汇总和工序明细时要求核对，避免重复。

使用 `npm run build`、`node tests/v10-engine.cjs`、`node tests/v10-bu.cjs` 和 `node tests/v10-data-center.mjs` 验证。导入用例依据 `Rw wip.zip` 中的 V3.8 VBS 导出代码构造。附件只有提取工具和说明，实际生成的 JSON、真实日报和公司电脑仍待验收。
